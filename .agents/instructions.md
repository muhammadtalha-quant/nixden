# Instructions for Agents in Nixden

## Project overview

Nixden is a NixOS and Home Manager flake for a personal multi-host configuration, built on [Den](https://den.denful.dev). It follows Den's Dendritic pattern: small Nix modules define reusable aspects, and host/user entities compose those aspects. The configured machine is currently `hp-probook-430g2`.

The desktop environment is managed through the `hyde` aspect and includes Hyprland, Noctalia, and Home Manager applications. Catppuccin is the visual theme. App settings and editor/desktop dotfiles are held alongside the modules that install them.

## Commands and validation

- `nix flake check` is the CI validation command. To reproduce CI, follow `.github/workflows/test.yml`: it creates `modules/ci-runtime.nix` setting `_module.args.CI = true` before running the check.
- `devenv shell` enters the development environment. `devenv.nix` provides `nixfmt`, `statix`, and the `nil` Nix language server.
- Format a Nix file with `nixfmt path/to/file.nix`, check its formatting without changing it with `nixfmt --check path/to/file.nix`, or lint with `statix check`.
- `devenv.nix` defines `compile`, `apply`, and `deploy`, mapped to `nh os boot`, `nh os test`, and `nh os switch`. These can build or activate the machine configuration; run them only when specifically asked to build, test, or activate the system.
- CI is flake-level; use the CI check as the validation target rather than inventing a single-test command or building a full host as a proxy.

## Flake and module architecture

- `flake.nix` is generated by `flake-file` and marked DO-NOT-EDIT. Declare/change inputs in `modules/entry.nix` under `flake-file.inputs`, then regenerate with `nix run .#write-flake`. The resolved inputs are recorded in `flake.lock`.
- `modules/entry.nix` enables the `flake-file` and Den Dendritic modules. The flake imports `modules/` recursively through `import-tree`, so Nix modules placed under `modules/` are discovered without a manual import list.
- Define reusable configuration as `den.aspects.<name>`. Aspects can define `nixos` and/or `homeManager` module scopes and use Den-provided context such as `host`, `user`, `pkgs`, and `inputs`. Compose behavior with `includes`.
- `modules/defaults.nix` provides shared composition: hostnames and host-defined users become Den entities, hosts include `nixos-core`, and `host.stateVersion` is forwarded to NixOS and Home Manager. Prefer reusable aspects for shared behavior over duplicating settings across host files.
- `modules/nixos-core.nix` holds common NixOS settings. Desktop and user-environment configuration primarily lives in the `hyde` aspect at `modules/hyde.nix`. Keep system settings under `nixos` and user settings under `homeManager`, even when both belong to the same aspect.
- For a user aspect that needs to configure its host, use Den's `provides.to-hosts.nixos` pattern as in `modules/users/muhammadtalha.nix`.

## Hosts, users, and schemas

- Host records are declared in `modules/hosts.nix`; host-specific aspects are in `modules/hosts/`. The current host module references its hardware facter report with `hardware.facter.reportPath`.
- User values are supplied in the host record and user-specific behavior is composed in `modules/users/`. This separates per-host identity data from reusable user settings.
- Accepted custom host and user fields are declared in `modules/schemas/host-schema.nix` and `modules/schemas/user-schema.nix`. When introducing a field, update the appropriate schema and populate/use it in the record or aspect.
- `stateVersion` is compatibility data; do not treat it as a routine release version or change it without a deliberate migration requirement.
- Host/user configuration contains password hashes and identity information. Do not reproduce those values in documentation, examples, or tool output.

## Hardware, storage, and system safety

- Reusable Disko layouts are Den entities under `modules/disko/`. A host selects a layout through its aspect includes and supplies machine-dependent values such as disk device and swap size through its host record.
- Disk layout and target-device changes can destroy data. Never run Disko formatting, partitioning, or installation commands without explicit user authorization.
- The `compile`, `apply`, and `deploy` scripts can change the running or bootable system. Inspect their effects and only execute them when the user specifically requests those operations.

## Desktop and dotfile wiring

- `modules/hyde.nix` connects NixOS system configuration and Home Manager user programs. Lua, TOML, and LazyVim source files are under `modules/_dotfiles/`.
- Hyprland Lua files are wired in `modules/hyde.nix` as named `extraLuaFiles`. Some are auto-loaded and some are required explicitly by other Lua modules. Preserve their module names and require/load relationships when adding or moving files.
- Noctalia uses `modules/_dotfiles/noctalia/config.toml`; LazyVim loads `modules/_dotfiles/lazyvim/`. Keep application-specific preferences in these existing files and change Nix wiring only when necessary.
- Keep hardware-specific settings in the relevant host data/aspect and shared desktop or user preferences in the shared aspect and dotfile layer.

## CI source of truth

`.github/workflows/test.yml` is the authoritative CI workflow. It runs for pushes and pull requests targeting `main`, installs Nix, creates the CI runtime module, and runs `nix flake check`. Update this workflow when changing CI behavior; do not rely on local-only or untracked runtime configuration.
